# 文件运行状态检查与修复方案

日期：2026-10-02。检查版本：`632afcb`。范围：PDF（含图片）、Excel、Word 工作区，以及任务中心的文件结果展示。

方案已于 2026-10-02 按用户确认实施，结果和验证范围见 [实施验证记录](validation/2026-10-02_file-status.md)。以下保留实施前的检查依据。

## 推荐用词

文件的主状态统一为 **待处理 / 处理中 / 已生成**。等待与处理可随着阶段切换，不把做过预处理当成一直正在翻译。

| 主状态 | 使用条件 | 补充说明示例 |
| --- | --- | --- |
| 待处理 | 等待本次任务执行下一步，没有该文件的处理工作正在执行 | 等待翻译、页面已处理 · 等待生成文件 |
| 处理中 | 该文件正在提取、翻译、审核或生成，也包括已提交但尚未返回的请求 | 提取文字、翻译页面 · 3 / 12 页已处理、生成文件、调整排版 |
| 已生成 | 所要求的最终输出已写好，针对该文件的后续写入工作已结束 | 有疑点时另标“需复核”；保留跳过页面和整份未翻译等现有提示 |

推荐“已生成”作为用户所说的“完成”对应词：仓库 `CONTEXT.md` 和任务中心已有这一约定，可以准确表示文件已经输出，同时不让用户误以为内容全部通过审核。任务整体仍使用“已完成”。

异常单独标明“未生成”“已停止”“应用中断”；停止后从未开始的文件显示“未开始”。明确跳过的文件保留“已跳过”。部分文件已经生成时，任务停止或失败不能覆盖这些文件的已生成结果。

暂停不等于所有请求都结束。未提交的工作暂停后，已发出的页面仍可能继续完成；这些文件应显示“处理中 · 等待已提交页面完成”，真正没有正在处理工作的文件才显示“已暂停”，并说明等待继续。

PDF 恢复操作的用户文案同步替换：

- “已排队 · 重新生成”改为“待执行 · 重新生成”。
- “已排队 · 跳过”改为“待执行 · 跳过”。
- 提示统一为“已安排重新生成／跳过，继续翻译后执行”。

这里去掉的是本地工作等待中的“排队”表述；接口限速风险提示仍应按真实含义表述，不能把实际远端限速解释成本地文件等待。

## 已确认的问题

### 1. 运行列表通过文件名猜状态，PDF 的聚合进度无法匹配

`ui/src/views/workspace.ts` 中：

- `initFileStages()` 将全部文件设成 `queued`。
- `handleTaskEvent()` 只在 progress/status 事件里调用 `markActiveFile()`。
- `markActiveFile()` 判断 `phaseName.includes(fileLabel(file))`，找不到文件名就不更新。
- `buildLogCard()` 将 `queued` 显示为“排队中”。

PDF 的 `_push_translation_progress()` 发送“翻译页面”和“正在翻译 PDF 页面，已完成 N / M 页”，两者都不包含文件名。复制文件和其他带文件名的信息主要是日志，而运行状态没有从这些日志更新。单文件任务同样会留在 `queued`。

PDF 逐页快照虽然已有文件和页面信息，`fetchPdfPagesSnapshot()` 却只更新 `pdfPagesSnapshot`，不会更新 `fileStage`。

### 2. Excel、Word 使用同一套猜测逻辑

普通 Excel/Word 文件的提取、翻译、生成阶段都大量发送不含文件名的聚合 progress/status 事件。Word 文件名出现在日志里也不会触发更新。

Excel 的旧格式转换、行高精调等特殊状态会带文件名，这些情况下列表可能暂时变成“进行中”；这不代表普通翻译过程已经正确。

### 3. 阶段切换被当成文件完成

`markActiveFile()` 匹配到另一个文件时，把前一个 `active` 文件改为 `done`，即使它只完成了提取文字，还没有写出译文。界面用“已进入下一步”回避了直接说完成，但这个状态仍不能表达文件实际所在阶段。

### 4. 停止、失败、中断时也会把所有文件改为 done

`handleTaskEvent()` 对 done、completed_with_issues、error、stopped、interrupted 共用同一个终态分支，将所有非 error 的文件设为 done。当前代码也没有逐文件设置 error 的路径。

`finishTask()` 会为上方表格整理真实逐文件结果，但下方运行列表依然读取这份被统一改成 done 的状态。因此一屏内可能出现相互矛盾的结果。

### 5. 上方文件表不读取运行状态

`buildTableRow()` 使用 `fileOutcomes`、续译信息和扫描预判，完全不使用 `fileStage`。`fileOutcomes` 主要在任务终态才填充。补充核对：活动任务期间这个表格实际被运行卡片替代，并非两个列表始终同时可见；问题是两套展示维护不同状态来源。修复让表格在显示时也优先读取同一份逐文件状态。

### 6. 接管正在运行的任务时没有恢复文件列表状态

`adoptExistingTask()` 调用 `focusTask()` 建立空 `fileStage`，随后订阅事件，没有调用 `initFileStages()` 或从后端恢复逐文件运行快照。重连、重新接管时不能只依赖当前页面的临时状态。

### 7. 任务中心没有相同的 queued 映射，但还没有逐文件实时过程

任务中心的文件结果表从终态 `file_results` / `files` 读取“已生成 / 未生成 / 未开始”等结果，没有工作区的文件名猜测逻辑。因此没有确认它存在同一个“全部排队中”的错误。但当前结果接口还不能给它提供完整的逐文件实时状态。

## 实际调度与状态语义

PDF 当前按照文件顺序提供页面，但页面进入共享的并行执行器。前一个文件的最后几页尚未结束时，后一个文件的页面可以开始处理，因此同一时刻允许多个文件处于“处理中”。

当前 PDF 常规路径先完成页面处理，再统一合成各文件的最终输出。因此“页面翻译已结束”不等于“已生成 PDF”；此时应显示“待处理 · 等待生成文件”。不在本次修复中改变合成时机。

Excel 和 Word 会先收集多份文件的文字，再合并去重并翻译，之后分别写出文件。因此不能硬套“文件 A 完成以后，文件 B 才开始翻译”的串行状态。正在参与当前处理的文件应显示“处理中”，并如实说明所在阶段；文件没有待翻译内容时不能假装正在请求模型。

## 推荐技术方案

1. **由执行器报告逐文件状态。** 执行器负责实际处理，在开始提取、参与翻译、等待写出、开始生成、生成结束、失败和停止等边界发送明确的文件事件。进度文字和运行日志只负责解释，不再兼任状态依据。
2. **每个文件有稳定标识。** 本次任务给扫描条目分配不含真实路径的文件 ID，事件、快照和终态结果都携带它。避免同名文件、不同目录和 `report.xls` / `report.xlsx` 被错误匹配，也继续遵守任务 API 不暴露源路径的约定。
3. **后端保留当前逐文件状态快照。** 快照是一次读取当前全部文件状态的数据；事件负责实时通知。断线重连和接管任务时先恢复快照，再接续事件，带版本号防止晚到的数据覆盖新状态。无需为本次界面修复变更用户数据 schema。
4. **一份状态数据供所有位置使用。** 上方文件表、下方运行列表和任务中心共用映射与结果判断，实时阶段优先于启动前的格式预判。续译复用页单独计数，不假装本次重新翻译过。
5. **逐文件依据最终结果收尾。** 从实际产物和逐文件结果决定“已生成 / 未生成 / 未开始 / 已停止”；不得以“整个任务结束”将全部文件标为完成。需复核、保留原文、占位页、整份未翻译等提示继续保留。

以上是实施前确认的技术方案；实际改动及限制见实施验证记录。

## 实施前的验证与限制

直接提取当前 `markActiveFile()` 函数及终态修改循环，用隔离数据执行了 6 项断言：PDF、Excel、Word 的不带文件名翻译状态都保留 queued；提取时切换文件会过早标 done；终态循环会将未开始文件统一标 done；上方表格不读取运行状态。

证据：`.runtime/self-tests/file-status-audit/current-behavior.json`。没有调用收费接口，也没有运行真实文档翻译。这个验证确认的是当前函数行为与代码契约，不是原生应用完整复现。

未修改应用代码，因此本轮没有运行代码交付用的质量门或 Tauri 开发壳测试。实施后必须补齐仓库质量门、前端构建、Rust 检查和隔离开发壳验证。

实施验收覆盖：单文件启动立即进入处理中；多文件真实开始与结束；PDF 跨文件并行；页面已结束但尚未合成；Excel/Word 合并文本阶段；同名文件和名称包含关系；暂停后在途请求完成；停止前/中/后、单文件失败不影响其他文件；断线和页面切换；续译与需复核；上下文件表和任务中心一致。
