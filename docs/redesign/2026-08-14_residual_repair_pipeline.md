# 残留中文治理：从「按量放行」到「按类修复」的流水线重构设计

- 日期：2026-08-14
- 状态：设计稿，待评审
- 实测语料：9 份真实双语施工方案（约 1119 个中法配对段落），全部为本项目历史交付件。文中以 文档A/B/C/D 指代，与真实文件的对照表存于本机 notes，不入库。
- 配套 PoC：[poc_residual_repair.py](poc_residual_repair.py)（本文所有机制均已在上述语料离线实测，不调 API 可复跑）

## 一、问题定义：三类系统性失败，一个共同根因

### 1.1 实测到的失败清单（全部来自已交付文档）

| 文档 | 失败形态 | 数量 | 现有系统的处置 |
| --- | --- | --- | --- |
| 文档A（2026-08-14 输出） | `（四）（五）` 序号未译，同级是 `(I)(II)(III)` | 2 | 放行 + 需人工复核 |
| 文档A | `rainure en V 型槽` 术语尾巴复读 | 3 | 放行 + 需人工复核 |
| 文档A | 节标题两套写法：`Section 1/3/5/6` vs `Deuxième/Quatrième/Septième section —` | 3 处离群 | **完全不可见** |
| 文档B（2026-06 输出，已交付） | `（二）` 序号未译 | 1 | 当时无此检测 |
| 文档C（已交付） | `第1节`~`第6节` 的「第…节」全部未译 | 6 | **完全不可见**（已交付业主） |
| 文档D（已交付） | `Deuxième section` 离群（其余为 `Section N`） | 1 | **完全不可见** |
| 翻译记忆库（当前生产状态） | `第一/三/五/六节→Section N`、`第二/四/七节→Nième section —` 两套写法已入库 | 7 条 | 无任何机制发现 |

三类失败：**结构序号残留**（（四）、第1节）、**术语尾巴复读**（型槽）、**文档级写法不一致**（节标题两套、且已被 TM 固化跨文档传播）。

### 1.2 共同根因

现行架构把「残留中文」当作**单段落的量的问题**：
`_light_residual_chinese_issue()`（translation_filter.py:612）以 `总汉字数≥4 或 占比>4%` 为阻断线。
而真实失败全部是**类的问题**：

1. 工程文档里最高发的残留恰是 1~3 字的序号和术语尾巴——永远够不到 4 字线。**阈值方向与失败分布正交**，调参无解：降到 1 字会把日期、专名、数量单位全部误伤，全文重译既烧钱又可能把好句子改坏。
2. 序号、标题写法是**文档级结构**，逐段校验在原理上不可见。`Deuxième section` 单看是完全正确的法语。
3. 唯一的修复手段是「整段重译」——重、贵、非定向，且对确定性失败无效（同一文档 3 处 `填充 V 型槽` 全部以相同方式失败，3 处 `沿裂缝开 V 型槽` 全部正确——这是模型的确定性行为；重试 prompt 已确认不含任何失败反馈，见 §4.4，不带反馈的重译只会复现）。

### 1.3 为什么不能继续打补丁

8/12 那轮修复（案例记录存于本机 notes）把「见汉字即否决」放宽成「少量放行」，方向正确（消除了 34 条误报），但把**报告分级**做成了**流程放行**。若这次再把 4 字线调成 2 字线，则日期（`2026年8月`=6 字会拦、`8月`=2 字不拦？）、专名、单位全部进入灰区，每修一类误报就制造一类漏报。**量的标尺上不存在正确的刻度**，因为要区分的从来不是多少字，而是那几个字是什么。

## 二、设计原则

1. **按类处置，不按量放行**：每个残留片段先分类（结构序号 / 术语尾巴 / 日期单位 / 数量单位 / 成句未译），每类有自己的修复通道和放行条件。
2. **修复阶梯，最便宜的先上**：确定性文本替换（0 API）→ 外科修补（小 prompt、diff 受限）→ 带反馈整段重译（最后手段）。
3. **保留原始翻译效果是硬约束**：所有修复只允许触碰残留片段本身及紧邻窗口；已通过的译文一个字不动。此约束由机器验收（diff 受限验收器），不靠模型自觉。
4. **文档级一致性是独立阶段**：序号惯例、标题写法在全篇写完后统一核查，逐段阶段不承担此职责。
5. **报告是台账的视图**：每个翻译单元从进入到落盘只有一条状态轨迹（台账），所有报告条目、底色、TM 写入决策都从台账推导——段号基准不一致、条目互相打架的问题从结构上消灭。

## 三、新架构

```
翻译单元 (unit)
  │  translate（现有批翻译，不动）
  ▼
[1] 逐段校验（现有 STRICT，不动）
  ▼
[2] 残留分类器 classify_residual_spans()     ← 新增，纯规则，0 API
  │    numbering_prefix ──→ [3a] 确定性修复（同级惯例探测 → 文本替换）
  │    term_fragment    ──→ [3b] 外科修补（小 prompt）→ diff 受限验收器
  │                            验收不过 → [3c] 带反馈重译（prompt 注明上次残留了什么）
  │    cn_date_unit     ──→ 阻断重译（现有规则保留）
  │    quantity_unit    ──→ 放行 + 台账记录（现有行为保留）
  │    sentence_block   ──→ [3c] 带反馈重译 → 语义仲裁（现有，保留）
  ▼
[4] 落盘（write_bilingual_docx，不动）
  ▼
[5] 文档级一致性巡检                          ← 新增，纯规则，0 API
  │    · 同级序号惯例（（X）→ (I)/(N) 系）
  │    · 章节标题写法（第X节 → Section N 系）
  │    离群 → 确定性前缀重写（只动前缀，正文不碰）
  ▼
[6] 台账定稿 → 报告 / 底色 / TM 写入
       TM 卫生：写入前做惯例归一 + 残留检查（双保险）
```

### 3.1 残留分类器（新增，`core/residual_classifier.py`）

对译文中每个 CJK 连续片段，按**它是什么**分类：

| 类别 | 判定 | 处置 | 理由 |
| --- | --- | --- | --- |
| `numbering_prefix` | 片段落在段首序号模式内：`（X）`、`X、`、`第X节/章/条`（X 允许汉字或阿拉伯数字） | 确定性修复 | 序号是闭集，目标写法可从同级段落推出，无需模型 |
| `cn_date_unit` | 现有 `_CN_DATE_UNIT_RE`（数字+年/月/日/元…） | 阻断重译（现状保留） | 8/12 已定的规则，实测有效 |
| `quantity_unit` | 片段 ⊆ {万, 亿} | 放行+记录（现状保留） | 无对应译法歧义小 |
| `term_fragment` | ≤3 字、嵌在成句目标语中间 | 外科修补 | 术语截断/复读，只需局部手术 |
| `sentence_block` | 其余（≥4 字或高占比） | 带反馈重译 | 真正的成句未译 |

实测：12/12 真实残留正确分类，约 1100 干净段落 0 误报（9 文档全量回放）。

### 3.2 确定性修复（新增）

**同级惯例探测**：只在「源段以同族序号开头」的段落里投票（避免被正文步骤编号污染），得出本文档惯例（如 `(I)(II)(III)` → paren_roman），无证据时退目标语默认。
**替换**：`（四）` → `(IV)`、`第1节 ` → `Section 1 `（fr）。纯文本替换，正文零接触。

实测：文档A `（四）（五）→(IV)(V)` 与同级对齐；文档C 六处 `第N节→Section N`；文档B `（二）→(2)`。9/12 处残留走此通道，0 API 成本。

### 3.3 外科修补 + diff 受限验收器（新增）

对 `term_fragment`：向模型发**单句**修补请求（原文 + 当前译文 + 指明残留片段），拿回修补稿后机器验收：

1. 残留已消除（复跑分类器，只允许 quantity_unit 级残留）；
2. **所有编辑操作都落在残留片段 ±12 字符窗口内**（SequenceMatcher opcodes 逐一检查）——模型顺手改了远处措辞、整句重写，一律拒收；
3. 数字集合完全不变。

拒收则升级到带反馈重译；再不过，进「需人工复核」，**原译文保留**（宁可保留可读的 99% 正确译文+标记，不用一个更差的重译覆盖）。

实测：6/6 验收用例判定正确（好修补两种放行；改远处措辞、改数字、整句重写、残留未除四种全部拒收，且给出可读拒收理由）。

### 3.4 带反馈重译（改造现有重试）

已确认（§4.4）：现有重试 prompt 是静态通用文案，载荷只有原文本身，零失败反馈——对确定性失败原理上无效。改造：重译请求附上「上一稿在此处残留了『X』，本稿不得出现任何中文」。相同源文本在提取阶段已合并为同一翻译单元（§4.1），修一处即全文档生效（本次 3 处 `型槽` 实为同一单元写到 3 个段落）。

### 3.5 文档级一致性巡检（新增，`core/document_consistency.py`）

全篇落盘后跑两类巡检（均纯规则）：

- **序号惯例**：同级段落序号形式归一（文档A 的 `(I)(II)(III)（四）（五）` 即使逐段全对也会在此被抓）。
- **标题写法**：源段 `第X节/章` 的译文前缀形式聚类，多数派为准，离群者做**仅前缀**重写：`Deuxième section — P...` → `Section 2 P...`。

实测：文档A 抓到 3 处离群并生成正确修复；文档D 抓到 1 处；干净文档 0 误报。

### 3.6 台账（重构报告层）

每单元一条记录：`unit_id, 源段锚点(源文档段号+文本指纹), 输出段锚点, 终态, 证据链`。
终态枚举：`clean / auto_fixed_deterministic / auto_fixed_surgical / retranslated_with_feedback / arbitration_accepted / released_with_note(quantity_unit) / needs_review / skipped(原因: front_matter|toc_field|header_footer|...)`。

- 报告 = 台账过滤视图，**所有条目统一用源文档段号锚定**，附输出段号为辅——消灭现状「仲裁条目用源段号、残留条目用输出段号」的双基准（本次报告中同一区域的问题以两套段号混排）。
- 底色 = 终态映射（只有 needs_review 上色，维持 8/12 定下的「底色只给需要人手的」）。
- 「无法读取的内容（内容控件 N 处）」：sdt 在台账里带类型（目录/其他），目录控件归入 `skipped(toc_field)`，不再进需复核清单吓人。
- 静默跳过归零：**台账全覆盖源文档每个可译单元**，任何单元不允许没有终态（8/12 发现的表题注静默跳过，在此结构下不可能复发）。

### 3.7 TM 卫生（新增两条规则 + 存量清洗）

1. **写入前惯例归一**：序号/标题前缀先按本文档惯例归一再入库（阻断 `Section N` 与 `Nième section` 混存——当前生产库已实存 4:3 两套，逐文档扩散中）。
2. **写入前复跑分类器**：任何带非 quantity_unit 残留的对不入库（现有排除规则只覆盖重试/仲裁接受的段落，此为结构性双保险）。
3. 存量清洗：`tm_cleaner` 增加一条惯例归一建议规则，清洗现有 7 条节标题（沿用「先建议、用户确认后写入」的既有流程）。

## 四、与现有代码的落点（代码地图已核实到行号）

### 4.1 提取与单元化（不动，但依赖其两个性质）

- `extract_word_segments`（word_document.py:340-423）：段落为翻译单元（跨 run 取全文），**相同源文本全文档去重为一个单元**（word_document.py:377-379，正文与表格共用同一 `seen` 集）。→ 修复结果天然全文档传播（§3.4）。
- 源侧段落锚点在提取时即存在（`segment_locations`，重试/仲裁报告条目在 word_task_runner.py:1197-1246 已在用）。台账的源锚点直接复用，无需新扫描。

### 4.2 分类器接线点

- `_evaluate_word_translation`（word_task_runner.py:1985-2027）是三条验收通道（批流 / 严格重试 / 语义仲裁）的唯一闸口。现状：strict 通过后仅凭 `has_residual_cjk` 布尔值（L2007-2011）挡下快速通道，随后 recovery 档在 L2023 以 `_light_residual_chinese_issue` 的量阈值放行。改造：布尔值换成分类器输出，评估结果携带 `[(span, category)]` 供池按类分流。
- `_light_residual_chinese_issue`（translation_filter.py:592-622）整体退役，`VALIDATION_PROFILE_WORD_RECOVERY` 的残留检查（translation_filter.py:526）改调分类器。

### 4.3 修复阶梯接线点

- `_WordRecoveryPool.add_candidate`（word_task_runner.py:2188-2228）：`numbering_prefix` 在此直接走确定性修复（0 API，同步完成），不进重试队列。同级惯例探测需要文档级上下文——由 runner 在建池时把全部 `(源, 首译)` 对注入池（现有池按源文本隔离，无此视野）。
- 外科修补复用单段重译的发送机械（word_task_runner.py:2409-2428 的 `translate_word_texts([source], ...)` 调用形态），换修补 prompt；验收器为新模块纯函数。
- `_build_word_retry_prompt`（word_task_runner.py:2781-2789）：现为静态通用附言 + 裸原文，改为接受结构化失败反馈。

### 4.4 已核实的现状事实（支撑设计前提）

- 重试零反馈：重试请求载荷就是 `[source_text]`，无任何「上次错在哪」的信息（word_task_runner.py:2409-2428、2781-2789）。
- 落盘后无任何环节能再改译文文本——post-write 只做底色与报告。→ 阶段 [5] 是新增的落盘后改写能力，属新机制。
- 报告双段号基准：重试/仲裁条目与 post-write 残留条目字符串格式相同（`body.paragraph[N]`）但基于不同文档（源 vs 输出，后者被插入的译文段推大）。→ §3.6 统一锚定的直接依据。
- `accepted_by == "strict_retry"` 并不严格等于 STRICT 字面通过（word_task_runner.py:2213/2451 按 `needs_review` 为假即赋值）。台账终态取代这套标签。

### 4.5 阶段 [5] 与 [6] 接线点

- 一致性巡检插在 `normalize_docx_automatic_numbering`（word_task_runner.py:1910 调用）之后、覆盖率复核标色（`apply_coverage_review_marks`）之前：只改既有段落的前缀文本、不增删段落，段索引稳定；先修后扫，覆盖率扫描看到的是修复后的文本。
- 报告组装 `_append_residual_cjk_issues`（word_task_runner.py:2979-3032）改为台账视图；sdt「无法读取的内容」产源在 word_task_runner.py:671，在台账中带类型归入 `skipped`。
- TM 写入路径 word_task_runner.py:1183-1306（排除集在 L1187-1188）：入库前加惯例归一 + 分类器复检。

### 4.6 顺带发现（不在本设计范围，另行处置）

- `_run_word_strict_retries`（word_task_runner.py:2678-2767）是完整实现但**从未被调用**的死代码，P3 动重试机制时一并清理。
- `quality_profile` 在 word_task_runner.py 全部调用点（1068/2425/2725）恒传 `None`，`_apply_word_quality_filter`（word_batching.py:487-512）永久空转，P2 清理。
- `_replace_cell_text` 行数不匹配回退（word_document.py:2203-2207）会静默清空表格单元格除首段外的源文段——独立缺陷，已单开任务卡。

## 六、保留翻译效果的三重保证

1. 已通过的译文零接触：修复只发生在带残留的单元，干净单元（实测 ≈95%）流水线行为与现在逐字节相同。
2. 一切修复过机器验收器，验收不过就回退原译文+标记，**不存在「修复把译文改差」的通路**。
3. 全量回放护栏：新增 `--replay` 只验不译模式（现有 CLI 无此能力），对历史 9 文档语料回放，要求：动作数 = 12+4（已知问题），其余全 clean。任何改动使干净段落出现新动作即 CI 失败。
