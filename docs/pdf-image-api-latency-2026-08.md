# PDF 页图接口延迟与浪费分析（2026-08-22 ~ 08-28 中转站账单）

数据源：中转站导出 `usage_2026-08-22_to_2026-08-28.csv`，1730 条，其中 `gpt-image-2` 125 条
（全部走 `/v1/images/edits`），`deepseek-v4-flash` 1600 条（`/v1/chat/completions`）。

## 1. 当前超时值

| 位置 | 常量 | 值 |
|---|---|---|
| `core/image_generation.py:35` | `IMAGE_GENERATION_TIMEOUT_SECONDS` | 180.0 s |
| `core/pdf_review.py:32` | `PDF_REVIEW_TIMEOUT_SECONDS` | 180.0 s |

`httpx.Client(timeout=180)` 对非流式的 `images/edits` 等价于「180 秒拿不到整包响应就放弃」。

## 2. 实测延迟分布（gpt-image-2，n=125）

p10 49s / p25 62s / **p50 88s** / p75 117s / p90 178s / p99 197s / max 208s，均值 100s。

**分布是双峰的，而且中间是空的：**

- A 段：29–117 s，94 次（75%）
- 空档：117–152 s，**0 次**
- B 段：152–208 s，31 次（25%）

超过 180 s 客户端超时线的有 10 次（8%）。这 10 次中转站照样按 $0.03 计费，但程序已经放弃、
把结果丢了，并且立刻再发一次全价重试。

## 3. 双峰的成因

| 证据 | 结论 |
|---|---|
| B 段 Output Tokens 6284–8971，A 段 710–4344，比值约 2.8× | 返回的图**本身**更大/更精细 |
| Input Tokens 两段完全重叠（5.2k–11.6k） | 与源图复杂度无关 |
| 发起时刻的在跑并发：A 段均值 8.76，B 段均值 8.77 | **与并发/排队无关**（排队会摊成连续分布，不会留 35 秒空档） |
| 请求的 `size` 由 `_pdf_page_size_for_model` 定死（A4/A3 同比例 → 1448×2048 ≈ 2.97MP） | 尺寸解释不了 2.8× |

唯一能解释 2.8× 输出 token 的是**质量档不同**。`_generate_page_with_images_edit` 的三档
回退里，第 1 档带 `quality=medium`，**第 2 档把 `quality` 整个丢掉**（服务端默认 = high/auto）：

```python
request_variants = (
    {**sized_data, "n": "1", "quality": "medium", "output_format": "png"},
    sized_data,                       # ← 没有 quality，服务端按 high 跑
    {"model": ..., "prompt": ...},    # ← 连 size 都没有
)
```

第 1 档只要被回一个 400 就静默升档。API Key 名字是「分发，稳定优先」——中转站在多个上游
之间分发，只要有一部分上游不认 `quality` / `output_format` / `n`，就会出现「同一批页里
25% 悄悄跑成 high 档」这种干净的双峰。

代价：B 段占 25% 的调用，却吃掉 **51% 的接口秒数**（5424s vs 5288s），单价还一模一样
（$0.03/次，与质量档无关）。等于花同样的钱，等两倍的时间。

## 4. 钱与时间的账

- 图片按次计费 $0.03（原价 $0.20，倍率 0.15），**与是否超时、质量档无关**。
- 本周图片支出 $3.75 / 125 次；文本 $2.85 / 1600 次。
- 超时丢弃的 10 次 = $0.30 白扔，且每次还占了 180 秒的并发槽 + 一次全价重试。
- 页重试上限 4 次（`PDF_PAGE_RETRY_ATTEMPTS_DEFAULT = 3` → attempts = 4）：最坏一页 $0.12、
  12 分钟。

## 5. 结论（按性价比排序）

1. **把 `quality` 钉死在每一档回退里**（第 2、3 档也带上）。预期把 B 段消掉，p90 从 178s
   降到 ~110s，整批墙钟时间省约 1/3。零成本变化。
2. **超时 180 → 240 秒**。图片是按次计费，超时不省钱只丢货：180 秒砍掉的是**真在干活**的
   请求（B 段尾巴 181–208s）。真挂死的请求多等 60 秒只多占并发槽，不多花钱。
   若第 1 条生效、B 段消失，再回调到 150 秒。
3. **每次调用记下「用了第几档变体 + 返回图的像素尺寸」**。这是确认第 3 节推断的一行探针，
   也是以后再出这种事的唯一凭据。
4. 并发 8–11 是健康的，不要按日志里那句「网络不稳定时可以把并发调低一些」去调低——
   数据显示慢的那批和并发无关。那句提示对超时错误是误导。

## 6. 进度条权重（另一条）

`ui/src/views/workspace.ts:2878` 把整条进度按阶段**均分**：
`percent = (phaseIndex - 1 + withinPhase) / phaseTotal`。

PDF 是 4 阶段（`core/pdf_image_translation.py`：预处理 / 翻译页面 / 生成最终产物 / 写入报告），
所以阶段 2 只占 25%–50% 这一段。而阶段 2 是 84 页 × ~100s / 并发 8 ≈ 17 分钟以上，
其余三个阶段全是本地操作、秒级。截图里「82/84 页 = 49%」正是这个 bug 的现场。

建议：progress 事件带上 `phase_weights`（PDF 用 `[0.05, 0.88, 0.05, 0.02]`），
UI 按权重折算，缺字段时退回均分。
